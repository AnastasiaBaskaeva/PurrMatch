# План доработки PurrMatch Android

Цель — готовое основное приложение на моковых данных по [product.md](product.md),
с MVVM + Clean Architecture, сохранением данных между запусками и заменяемыми
источниками данных. Существующие компоненты, ресурсы и оформление сохраняются;
реализованные сценарии переводятся на новую архитектуру постепенно.

План основан на коде от 21 октября 2026 года. Все изменения и документация остаются
в `android/`. Backend, общие API-контракты и отдельная админка в этап не входят.
Сравнение с Figma выполняется при реализации: наличие превью ещё не доказывает
соответствие макету 1:1.

## Предлагаемая архитектура

| Модуль                             | Ответственность и зависимости                                                                         |
|------------------------------------|-------------------------------------------------------------------------------------------------------|
| `domain` — новый Kotlin/JVM-модуль | Модели, контракты репозиториев, бизнес-сценарии и правила. Не зависит от Android, Compose, БД и data. |
| `data` — новый Android-модуль      | Моковые репозитории, локальная БД, сессия, файлы и адаптеры платформы. Зависит от domain.             |
| `presentation` — существующий      | UI, модели отображения, ViewModel и состояния. Зависит от domain, не от data.                         |
| `app` — существующий               | Создание зависимостей, Activity, навигация и запуск системных диалогов. Подключает остальные модули.  |

Начать с явного контейнера зависимостей в `app` и фабрик ViewModel. Отдельный DI-фреймворк
для текущего размера проекта не обязателен. Не создавать по модулю на каждый экран
или обёртку для каждого вызова репозитория.

ViewModel публикует `StateFlow<UiState>`, принимает действия и вызывает domain-сценарии.
На границе экрана состояние собирается с учётом lifecycle; существующие компоненты
получают значения и callbacks. Жесты, фокус и небольшое состояние отображения остаются
в UI. Черновики и аргументы экрана восстанавливаются отдельно от постоянных данных.
Такое разделение согласуется
с [рекомендациями Android по архитектуре](https://developer.android.com/topic/architecture/recommendations).

Для связанного набора пользователей, анкет и историй предлагается Room; для ID активной
сессии и небольших настроек — Preferences DataStore. Это сохраняет данные между
запусками и даёт транзакции для согласованных действий. Android рекомендует
[Room для структурированных данных](https://developer.android.com/training/data-storage/room)
и отделяет его
от [DataStore для небольших наборов настроек](https://developer.android.com/topic/libraries/architecture/datastore).
Версии и совместимость с текущими AGP/Kotlin проверяются при добавлении в version catalog.

Контракты репозиториев группировать по ответственности: аккаунт/сессия, профиль,
анкеты, персональные взаимодействия, верификация. Получение местоположения и доступ
к файлам скрывать за границами платформы. Use case нужен для составного действия
или правила, например публикации с проверкой прав, выбора карточки или удаления.
Не вводить общий `BaseRepository`, `BaseViewModel` или универсальный обработчик действий.

## Этап 0 Зафиксировать проверяемые сценарии

**Изменения:** расширить тестовые сценарии и подготовить fixtures рядом с тестами,
сохранить снимки текущих экранов для контроля миграции. Существующие тесты не считать
полным описанием требований: публикация сейчас проходит с автоматически подставленным фото.

Определить согласованный набор моковых данных: минимум два обычных пользователя,
верифицированный автор, заявки на рассмотрении и отклонённая, свои и чужие анкеты,
удалённая анкета в избранном, разные координаты, возрасты и условия передачи.
Начальные данные загружаются один раз; сброс — явное действие только для разработки/тестов.

До реализации соответствующих сценариев уточнить три детали, не блокируя основу:

- Момент учёта показа: требование говорит о показанных карточках. Предлагается
  фиксировать реальный показ, сохраняя текущую карточку для возврата из деталей;
  повторный запрос колоды уже исключает её. Рекомпозиция не должна записывать новый показ.
- Какие поля анкеты обязательны, как вводится местоположение без разрешения на геолокацию,
  допустимые формат и размер сертификата.
- Местоположение анкеты копируется при публикации или следует за последующими
  изменениями профиля. Актуальность контактов уже задана: они берутся из профиля автора.

**Приёмка:** каждому требованию из product.md соответствует сценарий проверки;
для неработающих сценариев зафиксирован ожидаемый результат. Проверки добавляются
по мере реализации, без обязательного создания заранее падающего набора тестов.

- Хранить дату рождения как дату, цену числом в выбранных минимальных единицах валюты,
  условия передачи и статус анкеты отдельными значениями. Тексты формировать в presentation.

  Возраст рассчитывать относительно подставляемой в тестах даты, не хранить вторую строку возраста.
- Создать локальную схему и репозитории; хранить просмотр и избранное по паре
  `userId + listingId`, а не как общие списки приложения. Удаление анкеты делать логическим,
  чтобы сохранить запись в чужом избранном.
- Моковая регистрация создаёт отдельную учётную запись; для демонстрации использовать
  только тестовые учётные данные, без требования вводить настоящие пароли.
- Добавить проверяемые ошибки чтения/сохранения в тестовых реализациях. Не создавать
  фиктивный HTTP-сервер или клиент несуществующего API.

**Приёмка:** после закрытия и запуска процесса данные не сбрасываются; истории
двух пользователей независимы. Повторная инициализация не восстанавливает удалённые
анкеты и не перезаписывает профиль. Domain собирается и тестируется без Android.

## Этап 2 Перевести вход и навигацию на MVVM

**Зависит от:** этапа 1. Это первый работающий сценарий на новой архитектуре.

**Файлы:** `app/.../MainActivity.kt`, новый контейнер зависимостей в `app`,
`presentation/.../App.kt`, `auth/LoginScreen.kt`, `auth/RegistrationScreen.kt`,
новые ViewModel и маршруты в presentation.

- Добавить ViewModel входа, регистрации и начального состояния сессии. Удалить
  принятие любых непустых данных; обрабатывать неверный вход и занятый логин на моках.
- При запуске дождаться чтения сессии и выбрать вход либо основную часть без краткого
  показа неправильного экрана. После регистрации сохранить пользователя и открыть заполнение профиля.
- Перевести строковую историю `App` на Navigation 3 с типизированными ключами и ID;
  сохранить три вкладки, системный Back и возврат из деталей к текущей карточке.
  Авторизация определяет доступность основной части; после выхода Back не возвращает в аккаунт.
- ViewModel привязать к времени жизни NavEntry; сохранять ключи и состояние записей
  стека, не создавать новую ViewModel на каждую рекомпозицию. Использовать штатные
  механизмы [Navigation 3](https://developer.android.com/guide/navigation/navigation-3)
  для [восстановления стека и областей ViewModel](https://developer.android.com/guide/navigation/navigation-3/save-state).
- Каталог и прямой запуск образцов оставить в debug. Пустое избранное и отсутствие
  результатов в основном приложении должны быть состояниями данных, а не отдельными
  искусственными маршрутами.

**Приёмка:** первый запуск → вход; успешный вход → Главная; перезапуск → основная
часть; выход → вход. Смена аккаунта не показывает чужие данные. Существующие экраны
сохраняют оформление во время переноса. `App` больше не является хранилищем мигрированных данных.

## Этап 4 Перевести колоду и избранное на персональные сценарии

**Зависит от:** этапов 1–3.

**Файлы:** `browse/HomeScreen.kt`, `favorites/FavoritesScreen.kt`,

- Выбирать доступные чужие непросмотренные анкеты через domain/data, убрать фильтрацию

- Учёт показа и выбор карточки выполняются одним управляемым сценарием. «Нравится»

- Сохранять текущую карточку при переходе в детали и назад; не возвращать уже показанные
  карточки при смене фильтров, выходе/входе и новом запуске.

приложение — анкета доступна только в его избранном, а не в новой колоде. История B
независима. Удаление автором не стирает запись из избранного A.

**Приёмка:** заявку можно подать, статус сохраняется после запуска; моковое решение
обновляет профиль и права публикации. Отклонение не даёт права платной передачи.

## Этап 7 Завершить публикацию и постоянное хранение медиа

**Зависит от:** этапов 1–3 и 6; интегрируется с этапами 4–5.

**Файлы:** `listing/NewListingScreen.kt`, `components/Photos.kt`,
`MainActivity.kt`, новая ViewModel формы, domain-сценарии публикации/удаления и data/media.

- Убрать автоматически добавленное фото и связь через индекс общего списка.
  Сохранять 1–4 выбранных изображения, порядок и обложку для конкретной анкеты.
- Обеспечить доступ к медиа после перезапуска: импорт в приватное хранилище либо
  постоянное разрешение чтения URI. Отмену выбора и ошибку чтения не считать успешным
  добавлением.
  Официальный [Photo Picker описывает сохранение доступа к URI](https://developer.android.com/training/data-storage/shared/photo-picker).
- Начинать новую форму с чистым черновиком; при пересоздании Activity восстанавливать
  незавершённый ввод, не смешивая его с фотографиями предыдущей анкеты.
- Публикация связывает анкету с текущим автором, местоположением и ссылками на медиа.
  Обычному аккаунту доступно только «Бесплатно», после одобрения — оба условия.
- Проверять права и цену в domain-сценарии, даже если UI скрывает платный вариант.
  Бесплатная цена всегда равна 0; повторный тап не создаёт вторую анкету.
- После публикации обновлять собственный профиль и подбор другого аккаунта.
  Удалять только свою анкету, логически исключать её из действующих; операция
  не удаляет чужое избранное. При отмене подтверждения данные не меняются.

**Приёмка:** A публикует кошку с выбранными фотографиями, B видит её в колоде;
A не видит собственную карточку. После перезапуска фото и анкета доступны.
B добавляет в избранное, A удаляет — B видит «Неактуально».

## Этап 8 Проверить дизайн и подготовить release на моках

**Зависит от:** завершения всех функциональных этапов. Визуальная проверка выполняется
также после каждого изменённого экрана, а не откладывается целиком на этот этап.

**Файлы:** компоненты, превью и тесты, `app/build.gradle.kts`, debug/release-исходники,
ресурсы, `README.md`, `AGENTS.md` и актуализация расхождений в product.md.

- Сравнить существующие экраны и состояния с Figma при одинаковом размере контента
  376×803 dp и шрифтах. Дополнительно проверить узкий экран, большой шрифт,
  клавиатуру, прокрутку, системные панели, TalkBack и доступные действия без жестов.
- Превью и снимки должны использовать фиксированные fixtures и дату, чтобы вычисляемый
  возраст не ломал визуальное сравнение. Сохранять компонентный каталог в debug.
- Проверить чтение больших выбранных фото и плавность свайпа на реалистичном числе
  анкет. Оптимизировать по измерениям; не вводить аннотации стабильности и кеши наугад.
- Включить release для `app`; убрать зависимость main-кода от debug-каталога и
  прямой обход входа через демонстрационные intent extras. Убедиться, что release
  сохраняет функциональность моков без инструментов управления тестовыми сценариями.
- Проверить release APK с R8, итоговый manifest и зависимые ресурсы; подготовить
  сборку AAB и способ локальной подписи без помещения секретов в репозиторий.
- Добавить предусмотренные новыми модулями unit-тесты и проверки хранения,
  обновить существующие UI-тесты, команды запуска и описание архитектуры.

**Приёмка:** готовый release на моках устанавливается и проходит основные сценарии;
нет заглушек, противоречащих product.md, и ошибок между аккаунтами. Подключение backend
будет отдельной реализацией репозиториев и адаптацией данных, не переписыванием экранов.
Фактические серверные DTO, авторизация и интеграционные проверки остаются частью
будущего подключения; без согласованного API их нельзя считать уже решёнными.

## Порядок и проверки готовности

Основной порядок: **0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8**.
Этап 6 допускается после 3, если нужно раньше проверить платную публикацию.
Каждый этап разбивать на небольшие работающие изменения; мигрированный сценарий
должен сразу использовать репозиторий, ViewModel и сохранение данных, а не второй
параллельный источник состояния внутри `App`.

После каждой правки — сборка, lint и установка/запуск на явно выбранном устройстве,
как требует [AGENTS.md](../AGENTS.md). Дополнительно:

- Domain: возраст, границы фильтров, исключение своих/просмотренных, права публикации,
  нулевая бесплатная цена и сохранение избранного при удалении.
- Data: транзакции, повторная инициализация, два аккаунта, сохранение после создания
  нового экземпляра хранилища и запуска нового процесса.
- ViewModel: загрузка, ошибка, успешное действие, повторное нажатие и восстановление формы.
- UI: вход/выход/повторный запуск, кнопки и свайп, переход анкета → автор → назад,
  фото, публикация, удаление, все статусы заявки и геофильтр при отказе в разрешении.
- Release: запуск без debug-каталога, полный сценарий A → B → A с перезапуском
  процесса, отсутствие приватного сертификата в публичном профиле.

Проверка `StateRestorationTester` сама по себе не подтверждает сохранение между
полноценными запусками приложения. Успешная запись PNG сама по себе не подтверждает
соответствие Figma; для этого требуется сравнение с макетом.
