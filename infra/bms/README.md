# Подготовка BMS и виртуальных машин PurrMatch

Этот набор команд готовит **новый выделенный сервер** с Ubuntu Server 24.04 x86_64: устанавливает QEMU/KVM и libvirt, создаёт две IPv4 NAT-сети и две независимые гостевые Ubuntu. Все команды на BMS выполняет оператор от root. CI и агент доступа к серверу не получают.

Скрипты восстанавливают инфраструктурную основу. PostgreSQL, k3s, приложение, пользовательские данные и облачные доступы здесь не устанавливаются и не восстанавливаются. Для переноса работающего приложения дополнительно нужны внешние резервные копии и проверенная процедура их восстановления.

## Поддерживаемый сервер

- Ubuntu Server 24.04, x86_64, Python 3, systemd, cgroup v2, включённый AppArmor, доступный `/dev/kvm`.
- Чистая конфигурация: без ранее установленных QEMU/libvirt, их конфигурации, гостевых машин и мостов libvirt. Скрипт не принимает существующую установку под управление.
- Хранилище образов на ext4. По умолчанию под диски гостей физически выделяется 400 GiB; дополнительно нужны место для ОС, кэша и минимум 20 GiB свободного остатка при создании каждого диска.
- Для одновременной работы стандартных гостей нужны 40 GiB гостевой RAM и 16 GiB запаса. Проверка доступной памяти выполняется перед каждым запуском через `vm.sh`.
- Оператор подтверждает право размещать собственные ВМ и отсутствие пересечения выбранного диапазона с подключёнными приватными сетями/VPN.

RAID, разметка, BIOS/BMC и swap хоста не изменяются. Адреса, MTU и маршруты физических интерфейсов намеренно не перенастраиваются. Libvirt создаёт мосты, включает IPv4 forwarding и добавляет необходимые NAT/filter-правила; возможны сопутствующие изменения forwarding/accept_redirects и LRO. Общая настройка firewall в этот набор не входит. NAT-сети сами по себе не доказывают изоляцию test от prod и хоста.

На уже подготовленном сервере повторять bootstrap не следует. При обнаружении существующих файлов, доменов или незавершённой операции скрипты останавливаются, сохраняя состояние для разбора. Одновременные операции блокируются общей блокировкой.

## Получение скриптов

После включения изменений в `infra/trunk` на новом сервере получите репозиторий и сохраните SHA выбранной версии:

```bash
git clone --branch infra/trunk --single-branch https://github.com/AnastasiaBaskaeva/PurrMatch.git /opt/PurrMatch
cd /opt/PurrMatch
git rev-parse HEAD
```

Далее команды выполняются из `/opt/PurrMatch`. Нужны root, доступ к официальным APT-репозиториям Ubuntu и `cloud-images.ubuntu.com`. Если `python3` отсутствует, сначала установите его из APT: `apt-get update`, затем `apt-get install --no-install-recommends --no-remove python3`. Git нужен только для получения кода.

## 1. Проверка и установка гипервизора

Проверка читает состояние сервера, ничего не устанавливая:

```bash
bash infra/bms/check-host.sh
```

Ожидаются KVM API version 12, AppArmor, cgroup v2 и подходящие ресурсы. Затем сформируйте план установки:

```bash
bash infra/bms/prepare-host.sh plan
```

Эта команда обновляет индексы APT, сохраняет исходное состояние, моделирует установку и скачивает пакеты без установки. Результаты лежат в `/root/purrmatch-bms/host/`:

- `preflight.txt`, `simulation.txt`, `versions.txt`, `apt-policy.txt` — исходные проверки и точный набор версий;
- `review/` — распакованные пакеты, maintainer scripts и systemd units;
- `packages.sha256` — контрольные суммы скачанных пакетов.

До установки просмотрите эти материалы, особенно изменение KSM в QEMU init/conffile, создание стандартной сети и запуск служб libvirt. План отклоняет обновление или удаление уже установленных пакетов. Необходимые обновления ОС выполняются отдельно; после изменения пакетов старый план недействителен. Незавершённый каталог не удаляйте ради повторного запуска — сначала выясните причину остановки.

Установка использует только проверенную локальную транзакцию. Первый запуск libvirt временно удерживается собственными systemd drop-in, чтобы стандартная сеть не стартовала автоматически:

```bash
bash infra/bms/prepare-host.sh install
bash infra/bms/prepare-host.sh start
```

Ожидаемый результат: libvirtd активен; гостевых ВМ и активных виртуальных сетей нет; сеть `default` сохранена, выключена и без autostart; TCP-порты управления 16509/16514 не слушаются. Состояние KSM и список мостов сравниваются с исходными. Существующие службы не маскируются и глобальная `policy-rc.d` не создаётся.

## 2. Сети test и prod

По умолчанию используется проектный диапазон `172.30.240.0/20`. В нём выделяются только первые две `/28`:

| Среда | Сеть | Шлюз/DNS | Адрес гостя | vCPU | RAM | Диск |
| --- | --- | --- | --- | --- | --- | --- |
| test | 172.30.240.0/28 | 172.30.240.1 | 172.30.240.2 | 4 | 8 GiB | 100 GiB |
| prod | 172.30.240.16/28 | 172.30.240.17 | 172.30.240.18 | 12 | 32 GiB | 300 GiB |

Выберите uplink по фактическому маршруту выхода в интернет:

```bash
ip -4 route show default
ip -brief address
```

В примерах ниже `etx2` — имя для замены на интерфейс вашего нового сервера. Сначала можно вывести XML без изменения хоста:

```bash
bash infra/bms/create-networks.sh --render test etx2
bash infra/bms/create-networks.sh --render prod etx2
```

После проверки диапазона и интерфейса создайте сети:

```bash
bash infra/bms/create-networks.sh etx2
```

Скрипт проверяет пересечение с адресами интерфейсов и конкретными маршрутами всех таблиц. Агрегатные маршруты RFC1918 и default не считаются занятыми подсетями; они также не подтверждают отсутствие удалённых VPN-сетей. Исходные маршруты должны сохраниться. Сети `purrmatch-test` и `purrmatch-prod` станут active/persistent/autostart; DHCP выдаёт только закреплённые адреса указанным MAC. `NO-CARRIER` у пустого моста до запуска гостя допустим.

## 3. Создание и проверка test

Создание скачивает чистый официальный Ubuntu cloud image по HTTPS и проверяет SHA256 по манифесту с того же официального сервера. Это проверка целостности в рамках доверия HTTPS, отдельная проверка подписи манифеста здесь не реализована. Версия источника и хеш сохраняются локально. Первый загруженный образ кэшируется; при пересоздании на другом BMS текущий официальный образ может отличаться.

```bash
bash infra/bms/create-vm.sh test
bash infra/bms/vm.sh test start
```

После загрузки гостя выполните проверку. Если SSH ещё не готов или NTP не синхронизирован, подождите и повторите только `check`:

```bash
bash infra/bms/vm.sh test check
```

Проверяются непривилегированный QEMU, AppArmor enforcing, действующие CPU/I/O limits, SSH, cloud-init, hostname, IPv4, KVM, число vCPU, NTP, DNS и публичный HTTPS. При первом подключении собственный `known_hosts` заполняется по TOFU; далее смена host key вызывает ошибку. Независимая проверка первого fingerprint оператором в эту автоматизацию не входит.

Проверьте штатную остановку и новый запуск:

```bash
bash infra/bms/vm.sh test stop
bash infra/bms/vm.sh test start
```

После загрузки снова выполните проверку. Напечатанный `Current boot ID` должен отличаться от `Previously checked boot ID`:

```bash
bash infra/bms/vm.sh test check
bash infra/bms/vm.sh test autostart enable
```

Autostart включается только после успешного `check` текущей загрузки. Проверка reboot всего BMS этими командами не выполняется.

## 4. Создание и проверка prod

Prod создаётся из исходного cloud image, с отдельными диском, seed, SSH identity и UUID. Диск test не клонируется:

```bash
bash infra/bms/create-vm.sh prod
bash infra/bms/vm.sh prod start
```

Дождитесь загрузки и успешной проверки:

```bash
bash infra/bms/vm.sh prod check
bash infra/bms/vm.sh prod stop
bash infra/bms/vm.sh prod start
```

После новой загрузки проверьте смену boot ID и включите autostart:

```bash
bash infra/bms/vm.sh prod check
bash infra/bms/vm.sh prod autostart enable
virsh -c qemu:///system list --all
free -h
df -hT /var/lib/libvirt/images
```

Обе ВМ должны быть running. Их диски физически выделены заранее; CPU ограничен квотой, начальный I/O ceiling каждого гостя — 100 MiB/s и 1000 IOPS. Эти значения требуют нагрузочной проверки для приложения. Проверка RAM перед `start` учитывает настроенную память активных гостей и 16 GiB запаса, но не создаёт отдельного host memory hard limit. Автозапуск libvirt и прямой `virsh start` не проходят эту проверку. Две ВМ на одном BMS сохраняют общий отказ хоста, RAID и сеть; это не HA.

## Изменение параметров для другого BMS

Перед созданием сетей и ВМ можно экспортировать проверенные несекретные параметры в root-shell:

```bash
export PURRMATCH_NETWORK_CIDR=172.30.240.0/20
export PURRMATCH_TEST_VCPUS=4
export PURRMATCH_TEST_RAM_MIB=8192
export PURRMATCH_TEST_DISK_GIB=100
export PURRMATCH_PROD_VCPUS=12
export PURRMATCH_PROD_RAM_MIB=32768
export PURRMATCH_PROD_DISK_GIB=300
```

CIDR должен быть выровненным приватным IPv4 `/20`. Используйте одно значение при создании сетей и соответствующих гостей. Размеры задаются положительными целыми; диск не может быть меньше исходного cloud image. Параметры не меняют уже созданную ВМ. `vm.sh` сверяет сохранённые UUID/IP и фактическую конфигурацию домена.

## Секреты и локальное состояние

В репозитории находятся только код, примеры параметров и этот гайд. Статические MAC и приватные CIDR не являются ключами доступа. Секреты Yandex Cloud и данные текущего сервера для bootstrap не нужны.

- `/root/purrmatch-bms/` — root:0700, планы установки и конфигурация; `vms/test` и `vms/prod` содержат отдельные приватные SSH-ключи с правами 0600 и `known_hosts`.
- `/var/lib/purrmatch-bms/` — проверенный кэш исходного cloud image.
- `/var/lib/libvirt/images/purrmatch-test` и `purrmatch-prod` — гостевые диски и seed. Диски/seed доступны `libvirt-qemu`, файлы имеют режим 0600.

SSH-ключи дают административный доступ к гостям через `purrmatch` и passwordless sudo. Не копируйте эти каталоги в Git, Actions artifacts или чат. Локальный `.gitignore` дополнительно исключает распространённые ключи, образы и runtime-файлы, но не заменяет проверку staged diff перед коммитом. После установки приложения образы дисков тоже становятся чувствительными данными.

Внешняя зашифрованная копия recovery secrets и доступ к личному облаку с backups должны переживать потерю исходного BMS. Создание bucket/IAM, резервирование данных и проверка restore выполняются отдельным этапом. Новые пустые ВМ получают новые ключи; восстановленные гости со старыми ключами требуют отдельной согласованной процедуры.

## Откат и незавершённые операции

Для остановки созданной ВМ сначала выключите autostart и затем остановите её штатно:

```bash
bash infra/bms/vm.sh test autostart disable
bash infra/bms/vm.sh test stop
```

Для prod используйте те же команды с `prod`. `stop` требует running и ждёт ACPI shutdown до 60 секунд; принудительное выключение и удаление данных не выполняются. Домены, ключи, диски и seed сохраняются. При ошибке после определения домена проверьте его через `virsh -c qemu:///system dominfo NAME`; не повторяйте создание поверх существующего состояния.

Откат сетей предусмотрен **до появления любых определённых ВМ**, в том числе выключенных, и при отсутствии других активных виртуальных сетей:

```bash
bash infra/bms/rollback-networks.sh
```

Он проверяет принадлежность сетей, выключает их autostart, останавливает их и восстанавливает сохранённые IPv4 forwarding/accept_redirects после проверки исходных маршрутов. Определения сетей и диагностическое состояние остаются. Общие firewall rules не очищаются; возможные изменения LRO со стороны libvirt не восстанавливаются. Это ограниченный откат созданных сетей, не полный снимок сетевого состояния хоста. Новый `create-networks.sh` поверх сохранённых определений намеренно завершится ошибкой.

Если `plan`, `install` или `start` оборвался, сохраните `/root/purrmatch-bms/host`, сообщение об ошибке и состояние пакетов/служб. Маркеры `install-attempted`, `start-attempted` и первый-start gate нужны для диагностики. Не удаляйте их, не снимайте gate и не запускайте purge вслепую. Автоматического отката APT или универсального продолжения частичной установки нет; восстановление выбирается после разбора конкретного состояния.

## Проверки кода

Без прав root можно проверить синтаксис, параметры, XML и отказ при ошибочных входных данных:

```bash
python3 -m unittest discover -s infra/bms/tests -v
```

При наличии `virt-xml-validate` проверяются также схемы libvirt. Два дополнительных теста выполняются только в специально подготовленном одноразовом root Docker-контейнере с `PURRMATCH_BMS_TEST_SANDBOX=1`: они используют фиктивный libvirt, синтетический диск и реальный `qemu-img`. Это проверки подготовки файлов, отказа от перезаписи и бюджета RAM; они не загружают настоящие ВМ и не проверяют установку systemd на BMS. Права на запуск этих fixture-тестов на рабочем сервере выдавать не следует.

Полная установка этого набора на новом BMS требует ручной проверки оператором. Успешный запуск пустых гостей не подтверждает восстановление приложения, сетевую изоляцию под нагрузкой или готовность к публичному production.

Изменения доставляются через PR в `infra/trunk`. В `main`, где пока разрешены только CI и branch policies, этот каталог переносить нельзя.

## Восстановление после потери BMS

1. Получить новый поддерживаемый сервер, проверить доступность KVM, ресурсы и свободные сети.
2. Выбрать проверенный Git SHA из `infra/trunk`, выполнить этот bootstrap и проверить оба cold start.
3. По отдельным инструкциям восстановить версии k3s/PostgreSQL, конфигурацию, данные и recovery secrets из личного облака; проверить восстановление сначала в test. Снимок работающего qcow2 сам по себе не считается согласованным backup PostgreSQL.
4. Проверить приложение, доступы, резервирование и сетевые политики. Переключать публичный DNS/трафик только после проверки prod.

Документация компонентов: [Ubuntu/libvirt](https://documentation.ubuntu.com/server/how-to/virtualisation/libvirt/), [libvirt networks](https://libvirt.org/formatnetwork.html), [libvirt domains](https://libvirt.org/formatdomain.html), [Ubuntu cloud images](https://cloud-images.ubuntu.com/).
